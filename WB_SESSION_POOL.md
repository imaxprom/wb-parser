# Пул WB-сессий

Реализован 12 октября 2026. До трёх независимых входов, одна рабочая сессия.
Интерфейс владельца: **Настройки → WB-сессии**. Дополнительные входы требуют
обычного подтверждения телефона кодом WB; копирование одной авторизации не создаёт резерв.

Телефон вводится один раз при добавлении и сохраняется в приватном реестре за слотом,
в том числе при неудачном или отменённом входе. Он показан в описании и на кнопке сессии.
При потере авторизации кнопка в актуальном списке становится «номер · Обновить сессию».
Повторное обновление сразу использует сохранённый номер, открывает чистый браузер и
запрашивает код; владельцу остаётся ввести код. Фоновое восстановление WB.ID по-прежнему
не запрашивает SMS. Изменить номер существующего слота нельзя — для другого нужен новый.

Миграция реестра v1→v2 извлекает номер из сохранённых полей аккаунта WB, не меняя токены
и активную сессию. Данные доставки, маскированные, зашифрованные и неоднозначные номера
не используются. Если номер старой сессии восстановить нельзя, бот запросит его один раз.
Публикация авторизации другого известного номера отклоняется с сохранением прежнего входа.

## Хранение и переключение

- `wb_sessions.py` — общий менеджер. `data/wb_sessions/registry.db` хранит реестр,
  состояния поиска/остатков, активный ID и поколение, журнал уведомлений.
- Секретные неизменяемые комплекты находятся в `data/wb_sessions/<id>/<revision>.json`.
  Каталоги 0700, файлы 0600. Cookies, browser state и WB.ID относятся к одному входу.
- SQLite-транзакция публикует только проверенную версию. Неудачный/отменённый вход
  сохраняет прежнюю версию. Слот, обслуживаемый браузером, нельзя удалить.
- Первичная миграция берёт старый `wb_session_refresh.lock`, согласованно читает
  существующие файлы и создаёт «Сессию 1» без повторного входа. `ready.json`
  появляется после фиксации миграции. Повторный запуск не создаёт дубликатов.
- Общий lock `switch` объединяет одновременные переключения. Блокировки `slot_<id>`
  изолируют вход/обслуживание отдельных сессий. Состояние recovery не блокируется
  на время сетевого запроса, поэтому параллельный 429 сохраняет общую паузу.
- `saved_at` активного снимка — поколение публикации/переключения. HTTP-запрос
  сохраняет его в заголовках как Python-атрибут (не отправляет WB) и в аудите.
  Старый ответ не может признать новую сессию неисправной. Аудит содержит `session_id`,
  но не cookies, токены, телефоны или текст запросов.
- Корневые session/browser/login JSON обновляются как совместимые экспорты для
  отката. Управляемые потребители читают SQLite и цельный комплект, а не эти экспорты.
  Старые отдельные скрипты входа запрещают перезапись файлов при включённом пуле.

## Ошибки и обслуживание

- 401: проверка доступных резервов; 403/498: не более одного резервного probe,
  затем ограниченное восстановление WB.ID. Автоматического возврата к старой сессии нет.
- 429 и серверный Retry-After сохраняют общую паузу, в том числе для резервных probe.
  Смена авторизации не сокращает этот срок. Округление срока — строго вверх.
- Проверки остатков валидируют резерв по реальному card endpoint. Их состояние
  отдельно от поиска: успешный поиск не означает успешные остатки.
- Один job существующего APScheduler запускается раз в минуту; резерв проверяется
  не чаще раза в 15 минут, после ошибки — с backoff. Во время обычной работы
  проверки уступают Telegram. При ожидании авторизации допускается восстановление
  резерва с приоритетом recovery, чтобы очередь не блокировала собственное восстановление.
- Требование SMS показывается владельцу. Автоматических запросов кодов нет.
  Периодический probe не гарантирует бесконечный срок жизни входа.
- Меню показывает давность проверки; «готова» устаревает через два интервала.
  Уведомления выдаются при изменении состояния и переключении, а не на каждый HTTP.

## Очередь и потребители

- `position_queue.db` хранит задания бота и результаты каждого завершённого ключа.
  Незавершённый ключ повторяется целиком. Массовая/плановая проверка сначала
  сохраняет все задания текущего пользователя, затем ожидает результаты.
- Процессный lock не позволяет двум обработчикам исполнять одну очередь.
  Восстановленные задания сохраняют приоритет бота; права пользователя проверяются снова.
- Отсутствие авторизации оставляет задания ожидающими. После перезапуска бот
  восстанавливает задания и отправляет результаты завершённых восстановленных проверок.
- `position_job_commits` в пользовательской БД обеспечивает идемпотентную запись
  результатов. Повторный Telegram-ответ возможен при падении строго между отправкой
  сообщения и отметкой о завершении; история позиций не дублируется.
- Очередь сайта уже хранится в PostgreSQL. Контракт `parser_busy` обозначает локальное
  ожидание авторизации и не расходует попытки сайта. Проверка готовности предлагается
  через 15 секунд; фактический recovery deadline остаётся сохранённым на стороне парсера.
  Это не даёт кешу внешнего Meta-only bridge задержать возобновление на несколько часов.
- Основной поиск, Geo/рекомендации и worker читают общую авторизацию. Geo/рекомендации
  сохраняют прежние глубину/параметры и собственную обработку ответов; исправление их
  отдельных алгоритмов не входит в эту миграцию. Worker пересоздаёт браузер при смене версии.

## Проверка и эксплуатация

Полный набор: `./venv/bin/python -m unittest discover -s tests -p '*_test.py'`.
Включены конкурирующее переключение, 429 во время восстановления, отказ/отмена входа,
изолированность заголовков, права, отдельный card probe, возврат очереди после SIGKILL
настоящего процесса и отсутствие повторной записи истории.
Также проверены миграция номера, запрет перепривязки, сохранение при отмене, повторное
нажатие, права владельца и браузерный сценарий заполнения телефона/запроса кода.

`WB_PARSER_DATA_DIR` позволяет запускать тесты на серверном Python с изолированными
данными. В production переменную не менять без переноса согласованных runtime-файлов.
При обновлении останавливать старые долгоживущие Meta-only SSH-процессы после выкладки:
их задания сохранены сайтом; новый процесс должен загрузить новые Python-модули.

Перед откатом: остановить исполнителей, проверить текущие очереди и актуальный
экспорт авторизации, сохранить SQLite средствами backup API и секретные комплекты
на том же сервере. Вернуть прежний код и согласованные legacy-файлы; новые БД не удалять.
Старая версия не возобновляет задания из `position_queue.db` — их нужно сохранить
до возврата исправленной версии. Не копировать local `.env`, БД или сессии на VPS.

Отчёт конкретной выкладки и результаты проверок: `data/session-pool-20261012/REPORT.md`.
